# Mr. Informer Blog

A static tech/AI/cybersecurity blog with no build step: plain HTML/CSS/JS frontend, a Python content pipeline, and Supabase as the backend. Deployed on GitHub Pages at `mr-informer.top`.

Read `CLAUDE.md` for architecture and commands, `PIPELINE_REPORT.md` for a full audit of the content pipeline's pros/cons, and `CHEATSHEET.md` for day-to-day operator tasks — this file is the short entry point that tells you which of those to open.

## Mental model

There are three layers, and mixing up which one is authoritative is the most common way to break this project:

1. **Supabase `articles` table** — the real source of truth. Written by the Python ingestion scripts (service-role key) and by the browser admin CMS (authenticated user, RLS-gated).
2. **`articles.json` / `articles.js`** — a local fallback cache, regenerated *from* Supabase, not hand-maintained. Never treat edits to these files as meaningful on their own; always regenerate them from Supabase after any real content change.
3. **`articles/<slug>/index.html` + `sitemap.xml`** — static, crawlable output generated by `generate_seo_pages.py`, also pulled fresh from Supabase. This exists because the homepage SPA (`index.html` + `app.js`) renders articles inside a JS-only modal that Google can't index.

If you change article content, the correct order is: change it in Supabase (or via the scripts that write to Supabase) → regenerate local JSON from Supabase → `python generate_seo_pages.py` → commit all three together.

## Non-negotiable product constraint

**No fabricated content.** This codebase used to invent fake headlines and hash-generated fake statistics when no real news was available, which is why it wasn't eligible for Google AdSense. That was removed. `pick_next_story()`/`run_sync()` in `news_workflow.py` publish nothing on a quiet cycle — do not reintroduce a "always publish something" fallback. Any article content must trace back to a real RSS item with a real source URL.

## Before pushing to GitHub

GitHub Actions auto-commits to `main` on a 3-hour cron. Check `git log HEAD..origin/main` before pushing; if the bot has committed since your branch started, merge and then **re-pull articles from Supabase + re-run `generate_seo_pages.py`** rather than trusting a raw git merge of `articles.json`. Full recipe in `CLAUDE.md` under "Pushing to GitHub from a sandboxed/non-interactive shell" (also covers the `/dev/tty` credential-helper hang and the `workflow` OAuth scope requirement for touching `.github/workflows/*`).

## Credentials

Local `.env` (gitignored): `SUPABASE_URL`, `SUPABASE_ANON_KEY`, `SUPABASE_SERVICE_ROLE_KEY`, `SITE_DOMAIN`. GitHub Actions has its own copies as repo secrets/variables — check `gh secret list` / `gh variable list` if something that should be automated isn't. The service-role key must never appear in any browser-shipped file (`supabase_client.js`, `index.html`, `app.js`, or the generated `articles/*` pages) — only the Python scripts use it.

Admin login is real Supabase Auth (Authentication → Users in the Supabase dashboard) plus a row in the `admins` table (`supabase_schema.sql`) — not a password anywhere in this repo.

## Where the domain is templated

`SITE_DOMAIN` env var drives `generate_seo_pages.py` and `news_workflow.py`. The four legal pages (`about/`, `contact/`, `privacy/`, `terms/`), `robots.txt`, and `index.html` are hand-written and hardcode the domain directly — update all of them together if it ever changes, then rebuild with `generate_seo_pages.py`.
